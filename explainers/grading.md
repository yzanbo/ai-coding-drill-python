# 答えの採点のされ方（エンジニアじゃない人向け）

このサイトでは、あなたが書いたプログラムの答えを **自動で採点** します。
人が目で見てチェックするのではなく、**コンピュータが実際にプログラムを動かして** 合否を判定します。

ここでは、「実行」ボタンを押してから、採点結果が画面に出るまで、
裏で何が起きているかを **絵と例え話だけ** で、まずはざっくり説明します。

> ℹ️ この流れは **今ちゃんと動いています**。
> 採点を担当する「職人」は、今は問題作りも **兼任** しています
> （同じ職人が 2 つの仕事を担当）。将来は採点専任に分ける予定ですが、
> やっていることは下の説明と同じです。

---

## いちばん大事な考え方は 2 つ

### ① 採点に AI は使わない

問題を **作る** ときは AI（人工知能）を使います。でも、答えを **採点する** ときは
**AI を一切使いません**。

理由は **公平さと再現性** です。AI に「この答えは何点？」と聞くと、
同じ答えでも日によって違う点数になったり、気分で甘くなったりしかねません。
そこで採点は、あらかじめ用意された **テスト（採点の基準）** に
あなたのプログラムを通し、**通るか・通らないかを機械的に判定** します。

例えるなら、**学校のマークシート試験の自動採点** です。
採点者の気分は一切関係なく、答えが基準と合っているかだけで○×がつく——
だから誰がやっても、何度やっても、**必ず同じ結果** になります。

### ② あなたが書いたコードを信用しない

あなたが送ったプログラムは、**何をするか分からない危険なもの** として扱います
（わざとサーバを壊そうとする悪意あるコードかもしれないからです）。

そこで、コードは **サーバ本体では動かさず**、外と切り離した
**使い捨ての箱（サンドボックス）の中だけ** で実行します。
箱の中で何が起きても、外には一切影響しません。

例えるなら、**防護壁に囲まれた検査室の中で、危険物を扱う** ようなものです。

## 登場人物（システム構成）

```
 ブラウザ    Backend API   ジョブキュー    Worker        Sandbox      Postgres
 (ユーザー)  (FastAPI)    (jobs テーブル) (Go)          (Docker)     (結果保管)
   👤        🏪            📋            🧑‍🍳          🧪           📚
```

各コンポーネントの役割（**例え名** は直感的に掴むための補助。本文・図ではコンポーネント名を使います）：

| コンポーネント | 例え名 | 役割 |
|---|---|---|
| **ブラウザ（ユーザー）** | あなた | 問題を解いて、書いた解答コードを送信する |
| **Backend API（FastAPI / Python）** | 受付 | 解答を受けて **ジョブを enqueue するだけ**。採点はせず即 `202` を返す（→ [ADR 0040](../docs/adr/0040-worker-grouping-and-llm-in-worker.md)） |
| **ジョブキュー（Postgres の `jobs` テーブル）** | やることリスト | 採点ジョブを貯める待ち行列。`SELECT FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY` で Worker に渡す（→ [ADR 0004](../docs/adr/0004-postgres-as-job-queue.md)） |
| **Worker（Go）** | 職人 | ジョブを取り出し、サンドボックス起動 → 結果書き戻しを実行する裏方（`apps/workers/grading`）。**採点に LLM は呼ばない**（→ [ADR 0016](../docs/adr/0016-go-for-grading-worker.md)） |
| **Sandbox（Docker コンテナ）** | 検査室 | あなたの解答を Vitest で実行し合否を判定。ネットワーク遮断・メモリ/CPU 制限・read-only・非 root・5 秒上限の隔離環境（→ [ADR 0009](../docs/adr/0009-disposable-sandbox-container.md)） |
| **Postgres（`submissions`）** | 結果保管庫 | 解答そのものと、採点結果（通過数・スコア・失敗の内訳）を永続化する |

> 🤔 なぜ Backend API（受付）と Worker（職人）を分けるの？
> 採点はサンドボックスを起動してプログラムを実行するため数秒かかります。
> API が同期で処理するとレスポンスが遅く・不安定になるため、API は **enqueue だけして即返し**、
> 重い採点処理は非同期で Worker に委譲します。ユーザーはすぐ「採点中…」画面に遷移でき、
> API のレスポンス時間も予測可能に保てます（→ [ADR 0040](../docs/adr/0040-worker-grouping-and-llm-in-worker.md)）。

## 全体の流れ（ざっくり版）

```
①解答送信               ②API が enqueue            ③Worker がジョブ取得
   👤 ブラウザ            🏪 Backend API             🧑‍🍳 Worker
   │ POST /submissions   │ submissions               │ SELECT FOR UPDATE
   │ {problemId, code}   │  + jobs に INSERT          │  SKIP LOCKED で claim
   │                     │  + NOTIFY                  │ (NOTIFY 受信 or
   │                     │ → 202 即返                 │  ポーリング)
   ▼                     ▼ (ブラウザはポーリング開始)  ▼
 ┌──────┐             ┌──────┐                  ┌──────┐
 │ API  │ ──────────►│ジョブ  │ ◄────────────── │Worker│
 │ 🏪    │             │キュー │                  │ 🧑‍🍳  │
 └──────┘             │ 📋   │                  └──────┘
                       └──────┘


④Sandbox で解答を実行    ⑤結果を判定               ⑥Postgres に保存
   🧪 Sandbox (Docker)    （AI は使わない）           status=graded
   │ 使い捨てコンテナで    │ ✅ 全テスト通過 → 正解     🧑‍🍳 Worker
   ▼ 解答を Vitest 実行    │ ❌ 一部失敗 → どこが×か     │ submissions UPDATE
 ┌──────┐             │ ⏱ タイムアウト(5秒超)     ▼ status=graded
 │Sandbox│             │ 💥 メモリ超過 / 構文エラー  ┌────────┐
 │ 🧪   │ ──────────► │   / 実行時エラー / 型エラー │Postgres│
 └──────┘             └──────┘ ───────────────►│ 📚     │
                                                 └────────┘
                                                      │
⑦ブラウザが完了検出 ◄──────────────────────────────────┘
   👤 ブラウザ
   │ ポーリングで status=graded を検出
   ▼ 採点結果（正解 / 失敗の内訳）を画面に表示
```

ポイントは ④と⑤の **「実際に動かして、決まった基準で機械的に判定する」** ところです
（「LLM の出力を信用しない」設計思想の、採点側の現れ）。

- **④ Sandbox（隔離実行）**：あなたの解答を、外と切り離した使い捨てコンテナの中だけで実行
- **⑤ 判定（決定論的チェック）**：用意されたテストに通るかどうかだけで合否を出す。**AI の主観は一切入らない**

### 採点結果は「合否」だけじゃない

ただ○×を出すのではなく、**なぜダメだったか** を種類ごとに分けて伝えます：

| 結果 | 画面の表示 |
|---|---|
| 全テスト通過 | 「正解」＋ 通過数 / 全数（例：5 / 5） |
| 一部のテスト失敗 | 失敗したテスト名・期待した出力・実際の出力・差分 |
| タイムアウト（5 秒超過） | 「タイムアウト」（無限ループなどが疑われる） |
| メモリ超過 | 「メモリ使用量超過」 |
| 構文エラー / 実行時エラー | エラー内容を整形して表示 |
| 型エラー（型パズル系のみ） | 型チェック（`tsc`）の結果を表示 |
| 一時的なシステムエラー | 自動で再試行。それでも失敗なら「再実行」ボタンを表示 |

## まとめ

```
   ┌────────────────────────────────────────────────┐
   │ 採点は AI を使わず、機械的に・公平に・再現性をもって行う │
   │                                                │
   │  Backend API は enqueue だけして 202 を即返す     │
   │  Worker が非同期でジョブを取り、Sandbox を起動      │
   │  Sandbox(Docker) で解答を実行（外と隔離・使い捨て）  │
   │  用意されたテストに通るかだけで合否を判定           │
   │  通過数・スコア・失敗の内訳を Postgres に保存       │
   └────────────────────────────────────────────────┘
```

ユーザーの操作は **問題を解いて「実行」ボタンを押すだけ**。
あとは API → ジョブキュー → Worker → Sandbox → Postgres の
非同期パイプラインが、**安全に・公平に** 採点して結果を届けます。

そして採点中、あなたのコードは **危険物として扱われ、隔離された箱の中だけ** で動きます。
だから、どんなコードを送っても、サーバ本体が壊れたり他の人に影響したりすることはありません。
